# Running NeuroBOLT on MASSIVE M3

## One-time

Account: **stay0060**, project **hz18**. Already filled into `~/.ssh/config`
and `scripts/m3_env.sh` — confirm with `ssh m3`.

**On an M3 login node:**

```bash
ssh m3
mkdir -p /projects/hz18/$USER && cd /projects/hz18/$USER
git clone https://github.com/soupeeli/NeuroBOLT.git
cd NeuroBOLT
bash scripts/m3_setup_env.sh
```

Then place by hand, **on the login node** (compute nodes may have no internet):

- `checkpoints/labram-base.pth` — <https://github.com/935963004/LaBraM/tree/main/checkpoints>
- EEG / fMRI data under `/scratch/hz18/stay0060/NeuroBOLT/data/` — <https://huggingface.co/datasets/NeurdyLab/NeuroBOLT>

**Connect VS Code to the login node once** (`Remote-SSH: Connect to Host` → `m3`).
That installs `~/.vscode-server` into your home directory, which is shared with the
compute nodes — so the compute-node connection reuses it rather than trying to
download it over an interface that may be firewalled.

> Verified 2026-09-20: M3 runs Rocky Linux 9.8 with glibc 2.34, comfortably above the
> 2.28 that current VS Code requires. Remote-SSH works.

## Each session

```bash
ssh m3
bash scripts/m3_session.sh 8        # holds 1 GPU for 8h; prints the node
```

Locally:

```powershell
powershell -ExecutionPolicy Bypass -File scripts\m3_connect.ps1
```

Then in VS Code: `Ctrl+Shift+P` -> **Remote-SSH: Connect to Host** -> `m3-node`.
Open `/projects/hz18/stay0060/NeuroBOLT`, and select the interpreter at
`/projects/hz18/stay0060/miniforge3/envs/neurobolt/bin/python`.

**Release the GPU when you are done:** `scancel <jobid>` (or `scancel -n nb-session`).
The holder job sits on the GPU until its time limit whether or not you are using it.

Sanity check in the VS Code terminal:

```bash
nvidia-smi
source scripts/m3_env.sh && activate_neurobolt
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
```

You get the job's GPU and CPU limits over plain SSH because SLURM adopts the SSH
session into the job's cgroup -- which is why `--num_workers 8` should match
`--cpus-per-task=8`.

### After a VS Code update

The remote server is tied to VS Code's exact commit sha, so an update means a new
download on first connect. Compute nodes do have internet, so this works on its own --
but to pre-seed it (and fail loudly now rather than mid-connect):

```bash
bash scripts/m3_vscode_server.sh <commit-sha>
```

Get the sha from the third line of `Code.exe --version`, or `commit` in
`resources/app/product.json`. Seeded so far: 1.137.0 and 1.138.0.

## Gotchas

### `requirements.txt` installs nothing

Upstream puts `--no-deps` inline on the first requirement:

```
linear-attention-transformer==0.19.1 --no-deps
```

That is not a valid per-requirement option, so modern pip rejects the **entire file**
with `no such option: --no-deps` and installs nothing at all — you are left without
mne, timm, pandas and the rest, and only find out at the first import.
`scripts/m3_setup_env.sh` splits it into a `--no-deps` pass and a normal pass.

### The env silently breaks on unrelated conda installs

torch 2.0.0 needs `numpy < 2` (else `RuntimeError: Numpy is not available`) and
`mkl <= 2024.0` (else `import torch` fails on the removed `iJIT_NotifyEvent` symbol).
Any later `conda install` can pull either one forward, so both are pinned in
`$CONDA_PREFIX/conda-meta/pinned`. Leave that file alone.

### `set -u` fights conda

conda's activate/deactivate hooks reference unset variables, so a script using
`set -euo pipefail` aborts mid-run with
`CONDA_MKL_INTERFACE_LAYER_BACKUP: unbound variable`. The setup script uses
`set -eo pipefail` for this reason.

### HuggingFace directory names do not match the loader

The dataset ships `EEG_set/` and `fMRI_difumo64/`; `dataset_maker/get_datasets.py`
expects `EEG/` and `fMRI_difumo/`. Filenames inside already match.
`scripts/m3_fetch_data.sh` remaps the directories on download — a plain
`huggingface-cli download` would leave you with a `FileNotFoundError`.


### cuDNN aborts on the first convolution

torch bundles its own cuDNN at `site-packages/torch/lib/libcudnn_cnn_infer.so.8`,
which `dlopen`s the **unversioned** `libnvrtc.so`. conda ships only
`libnvrtc.so.11.2`, and `LD_LIBRARY_PATH` is empty under SLURM, so the process
core-dumps at the first conv — after the model and data have loaded, which makes it
look like a model bug:

```
Could not load library libcudnn_cnn_infer.so.8
Error: libnvrtc.so: cannot open shared object file
```

Fixed by a `libnvrtc.so` symlink plus an `activate.d` hook that puts
`$CONDA_PREFIX/lib` on `LD_LIBRARY_PATH`. The hook fires on every activation, so the
VS Code Python extension gets it too.

### `epochs <= warmup_epochs` dies with a bare AssertionError

`--warmup_epochs` defaults to 5. `utils.cosine_scheduler` builds
`warmup_epochs * niter_per_ep` warmup entries but asserts the total is
`epochs * niter_per_ep`, so any short debugging run fails at startup with no
explanation. Lower `--warmup_epochs` whenever you lower `--epochs`.

### `$(dirname "$0")` is wrong inside sbatch

SLURM copies the batch script to `/var/spool/slurmd/job<id>/` before running it, so
`$0` is not in the repo. The sbatch scripts use `${SLURM_SUBMIT_DIR}` instead.

### sbatch rejects CRLF

Editing these scripts on Windows can introduce `
`, which sbatch refuses outright
(`Batch script contains DOS line breaks`). Keep them LF.


### smux cannot be scripted

`smux new-session` needs a TTY and then attaches you to tmux, so it fails over a
non-interactive ssh (`open terminal failed: not a terminal`). Its flags also differ
from sbatch's: `--cpuspertask`, not `--cpus-per-task`. `scripts/m3_session.sh` uses a
`sleep infinity` batch job instead -- for Remote-SSH all you need is a live allocation,
since SLURM lets you ssh to any node where you have a running job. For a tmux session,
use `ssh -t m3 'smux new-session ...'`.

### Windows PowerShell mangles quoted native-exe args

`ssh m3 'squeue -o "%T %N"'` arrives at squeue split in two
(`Unrecognized option: %N`). `m3_connect.ps1` uses a comma-separated format with no
inner quotes and no spaces.

### Distributed init needs MASTER_ADDR under SLURM


[`utils.py:417`](../utils.py#L417) branches on `SLURM_PROCID`, sets `distributed = True`,
but leaves `world_size` at its default of `1` and `dist_url` at `env://` — which then
reads `MASTER_ADDR`/`MASTER_PORT` from the environment and crashes if they are unset.

- **In the VS Code terminal this does not bite.** An SSH session does not inherit SLURM's
  environment, so `SLURM_PROCID` is absent, the code prints `Not using distributed mode`,
  and runs single-GPU.
- **Under `sbatch`/`srun` it does.** `scripts/train_m3.sbatch` already exports both.
  To sidestep DDP entirely instead: `env -u SLURM_PROCID python main.py ...`
